# Configuration Reference

Every field of the nbkp YAML config file, with its type, default, and validation
rules. For users writing a config file who need the exact shape of a section.

For what the entities *are* and how they relate (volumes, endpoints, syncs,
snapshots), read [Domain](./domain.md) first. For runtime behavior, see
[Internals](./internals.md). For worked examples, see [Usage](./usage.md#config)
and [config-examples/](./config-examples/).

Everything between a `<!-- BEGIN CONFIGREF:… -->` and its `<!-- END … -->`
marker is generated by `mise run configdocs` and overwritten on the next run,
prose included. Edit it at its source instead: a field's description in the
`description=` of its `Field` in the config models (`nbkp/config/protocol/`),
and the notes under each table, the top-level structure block and the
discriminator rows in `build-scripts/configdocs.py` (`_TOP_LEVEL_STRUCTURE`, the
`_*_NOTES` constants and `_DISCRIMINATOR_OVERRIDES`). Only the prose outside the
markers is edited here.

## Config File Location

nbkp searches for the config in this order and uses the first match:

1. Explicit `--config` path
2. `$XDG_CONFIG_HOME/nbkp/config.yaml`, or `~/.config/nbkp/config.yaml` when
   `XDG_CONFIG_HOME` is unset, empty or not an absolute path
3. Platform user config dir (Linux: same as above; macOS:
   `~/Library/Application Support/nbkp/config.yaml`)
4. Platform site config dir (Linux: `/etc/xdg/nbkp/config.yaml`; macOS:
   `/Library/Application Support/nbkp/config.yaml`)

Platform directories are resolved using
[platformdirs](https://github.com/tox-dev/platformdirs).

## Volumes

**Path normalization** — Volume paths and sync endpoint subdirectories are
normalized at load time: trailing slashes are stripped, so `path: /mnt/data/`
and `path: /mnt/data` are equivalent. A `subdir` also drops its empty and `.`
segments (`subdir: ./photos//2024/` is `photos/2024`), and one containing a `..`
segment is rejected: a subdir must name a directory inside its volume. For local
volumes, `~` is expanded to the current user's home directory (`path: ~/data`
becomes `/home/user/data`). Remote volume paths are not `~`-expanded: there the
tilde refers to the remote user's home and is resolved by SSH/rsync on the
remote side.

**`path` and `mount`** — `path` is required unless the volume declares a `mount`
section. For a mount-managed volume, declare `path` (backed by an `/etc/fstab`
entry) to mount at a fixed location, or omit it to let udisks mount at
`/run/media/<user>/<label>`, which nbkp discovers at runtime. There is no
`strategy` field (udisks is the only backend) and no `mapper-name` (nbkp
discovers the name udisks chose for the unlocked device). See
[Volume Mount Management](./internals.md#volume-mount-management) and the
[udisks2 setup guide](./usage.md#mount-management-with-udisks2).

| Field | Type | Default | Description |

Top-level config fields for credential retrieval:

| Field | Type | Default | Description |
|---|---|---|---|
| `credential-provider` | `"keyring"` \| `"prompt"` \| `"env"` \| `"command"` | `"keyring"` | How LUKS passphrases are retrieved |
| `credential-command` | list of strings | `null` | Command template for `command` provider. Must contain `{id}` placeholder (e.g. `["pass", "show", "nbkp/{id}"]`). A leading `~` in the program (the first item) is expanded |

Providers:
- **keyring**: `keyring.get_password("nbkp", passphrase_id)` — uses macOS Keychain or
  Linux SecretService. Requires `uv tool install 'nbkp[keyring]'`.
- **prompt**: interactive hidden input prompt.
- **env**: reads `NBKP_PASSPHRASE_<ID>`: the passphrase-id uppercased, with every
  character other than a letter or digit replaced by `_` (`nas.disk-1` →

  (`usb-drive` and `usb_drive`) are rejected when the config loads.
- **command**: runs command template with `{id}` replaced by passphrase-id. The first
  line of its output, without the line break, is the passphrase (the `pass` convention:
  later lines hold metadata); spaces are kept.

## SSH Endpoints

**`extends`** — An endpoint inherits every field of the endpoint it extends and
overrides only the fields it sets. `connection-options` is merged the same way,
option by option: a child that sets only `compress` keeps the parent's
`known-hosts-file` and timeouts. One level only: a child's `disabled-algorithms`
replaces the parent's. Setting one field of a mutually exclusive pair
(`proxy-jump` / `proxy-jumps`, `location` / `locations`) drops the inherited
other half. Circular `extends` chains are rejected at load time.

**`proxy-jump` / `proxy-jumps`** — Reference other endpoints by slug to reach
the host through one bastion (`proxy-jump`) or a multi-hop chain
(`proxy-jumps`). Hops are traversed in order, like SSH's `-J`, but nbkp does not
use `-J`: the rsync and generated-script SSH commands nest one
`-o ProxyCommand=ssh … -W %h:%p <hop>` per hop, so each hop gets its own port,
key and `connection-options` (with `-J`, a hop's options would come only from
`~/.ssh/config`), and Fabric/Paramiko opens each hop as a gateway connection.
See [SSH transport](./internals.md#ssh-transport). A hop may have its own
`proxy-jump(s)`: nbkp reaches it through its chain first, so `proxy-jump: b1`
where `b1` jumps through `b2` connects through `b2`, then `b1`. A bastion that
several hops share is jumped through once, where it is first needed. Circular
chains are rejected at load time.

**`location` / `locations`** — Network-context tags (e.g. `home`, `travel`)
consumed by `--location` / `--exclude-location` at runtime. See
[Endpoint Filtering](./internals.md#endpoint-filtering).

**`~/.ssh/config` enrichment** — `port`, `user`, and `key` (first
`IdentityFile`, `~`-expanded) are filled from `~/.ssh/config` when not set.
Precedence, highest first: explicit value > inherited via `extends` >
`~/.ssh/config` > default. `proxy-jump` and `connection-options` are never
enriched. A `Port` there that is not a number, for an endpoint that does not set
`port`, is a config error: the command exits with code 2, and with
`--output json` prints `{"error": {"reason": "invalid-ssh-config", ...}}`.

**Connection options** — Typed SSH settings mapped onto the SSH CLI (used by
rsync) and onto Paramiko/Fabric (used by checks and snapshot operations).
`channel-timeout` and `disabled-algorithms` only apply to the Paramiko/Fabric
path. **Host key verification** — Both paths verify the host key the same way.
With `strict-host-key-checking: true` (the default), the host's key must already
be in `~/.ssh/known_hosts` or in the system-wide `/etc/ssh/ssh_known_hosts`
(OpenSSH's default `GlobalKnownHostsFile`), or in `known-hosts-file` when it is
set (it replaces `~/.ssh/known_hosts`, like OpenSSH's `UserKnownHostsFile`; a
missing file counts as empty). With `known-hosts-file` set, nbkp's own checks
consult only that file, while OpenSSH, behind rsync, still also trusts the
system-wide one. nbkp never trusts a new host on first use: an unknown host or a
changed key is refused, and preflight reports it as
`ssh authentication or host key verification failed` (`auth-failed` in JSON
output). Add a new host once with `ssh <host> true`, after checking the
fingerprint it shows against the host's own
(`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the host), or with
`ssh-keyscan` when the fingerprint is checked another way. With
`strict-host-key-checking: false`, any key is accepted. OpenSSH, behind rsync,
records a new key in the known-hosts file; nbkp's own checks accept it for the
run without recording it. Setting
`strict-host-key-checking: false` together with `known-hosts-file: /dev/null`
fully disables host key verification and persistence, which suits ephemeral
hosts whose keys change on reprovisioning. `key` and `known-hosts-file` are
`~`-expanded at load time. The resulting SSH flags are listed in
[SSH transport](./internals.md#ssh-transport).

## Syncs

**Rsync options** — `compress` and `checksum` are opt-in flags.
`default-options-override` replaces the default flags entirely; `extra-options`
appends flags after them. Why `--hard-links` is not a default:
[Rsync Defaults](./internals.md#rsync-defaults).

**Vanished files** — When a file disappears from the source between rsync's
scan and its transfer, rsync copies everything else and exits with code 24. By
default (`vanished-files: fail`) the sync fails like any other rsync error: a
new hard-link snapshot is discarded, `latest` stays where it was, and downstream
syncs are cancelled. With `vanished-files: warn` the sync succeeds: its snapshot
is published, `latest` moves to it, and the result carries a `vanished-files`
warning. A source that is in use while it is backed up, such as a home
directory, loses a file this way on many runs; `warn` keeps those runs from
failing. Any other non-zero rsync exit still fails the sync. The generated `sh`
script behaves the same way.

#### Filters

Filters can be specified as structured rules or raw rsync filter strings, mixed freely:

```yaml
filters:
  # Structured include/exclude rules
  - include: "*.jpg"          # becomes "+ *.jpg"
  - exclude: "*.tmp"          # becomes "- *.tmp"

  # Merge: read rules from an external file (applied globally)
  - merge: /etc/nbkp/extra-rules.txt
  - merge: ~/my-rules.txt    # tilde is expanded

  # Dir-merge: per-directory filter files (rsync discovers them as it walks the tree)
  - dir-merge: .rsync-filter

  # Dir-merge with exclude-self: equivalent to rsync's -FF
  # (use per-directory filters, but don't transfer the filter files themselves)
  - dir-merge:
      path: .rsync-filter
      exclude-self: true

  # Raw rsync filter strings (for advanced modifiers like ,e or ,n)
  - "H .git"                  # hide .git from transfer
  - "- __pycache__/"          # exclude __pycache__
  - "dir-merge,e /.rsync-filter"  # dir-merge with word-splitting
```

**`merge`** reads a file of filter rules once and applies them at the point where they
appear in the list. Tilde (`~`) is expanded in merge paths. This is similar to
`filter-file`, but `filter-file` is always appended after all inline filters, while
`merge` respects its position in the list.

**`dir-merge`** tells rsync to look for the named file in each directory as it walks the
source tree. Rules from each file apply only to that directory and its subdirectories.
The `exclude-self` option appends a `- <filename>` rule to prevent the filter files from
being transferred (equivalent to rsync's `-FF` flag). Dir-merge paths are not
tilde-expanded (they are relative filenames resolved by rsync per-directory).

Each structured rule is a mapping with exactly one key: `{include: "*.jpg", exclude:
"*"}` is rejected rather than read as one of its rules. Write two list items instead.

Filters are applied in order as `--filter=RULE` arguments. When `filter-file` is also
set, inline filters are applied first.

## Validation Rules

Checked when the config is loaded, before anything runs:

- Slugs are lowercase alphanumeric with hyphens, at most 50 characters.
- An entry's slug is the key it is declared under. An entry may also write
  `slug`, but only with that same value: a different one is rejected
  (`slug-mismatch`), since some lookups go by key and others by slug.
- Every key must be one this page documents: an unknown key, such as a misspelt
  `max-snapshot` or `hard-link-snapshot`, is rejected (`extra_forbidden`) with
  its location, rather than ignored while its section falls back to the
  defaults.
- Every slug reference (`ssh-endpoint`, `ssh-endpoints`, `proxy-jump(s)`,
  `extends`, `volume`, `source`, `destination`) must name an existing entry.
- No circular `extends` or `proxy-jump` chains. Two hops sharing a bastion (e.g.
  `proxy-jumps: [b1, b2]` where `b1` itself jumps through `b2`) is not a cycle.
- `proxy-jump` / `proxy-jumps` and `location` / `locations` are mutually
  exclusive.
- Each sync endpoint targets a unique `(volume, subdir)` pair, and no endpoint
  may be nested inside another on the same volume (e.g. `subdir: photos` and
  `subdir: photos/2024`): sync dependencies cannot be detected between
  overlapping paths. The check compares subdirs within one volume only: it does
  not see two volumes whose paths overlap (`/mnt/a` and `/mnt/a/b`, or a remote
  `~` and an absolute path on the same host), so endpoints on such volumes can
  overlap undetected. Declare a directory tree as one volume and split it with
  `subdir`s rather than as nested volumes.
- A sync endpoint's `subdir` has no `..` segment.
- At most one of `btrfs-snapshots` and `hard-link-snapshots` is enabled per sync
  endpoint.
- A sync's `source` and `destination` are different endpoints.
- Each sync endpoint is the destination of at most one sync.
- Syncs must not depend on each other in a cycle (e.g. `a: x → y` and
  `b: y → x`): the backup graph must have a topological order.
- A remote-to-remote sync must stay on one server: both volumes must offer the
  same SSH endpoints, in the same order (their `ssh-endpoints` lists, or their
  `ssh-endpoint` when the list is absent). The run reaches both paths through
  the destination's endpoint, and each volume picks its endpoint from its own
  list, so two different lists could land on two different hosts.
- A volume without a `mount` section must declare `path`.
- A local volume's `path` must be absolute once `~` is expanded: a relative path
  would resolve against whichever directory nbkp is started from.
- `credential-command` is required when `credential-provider` is `command`, and
  must contain the `{id}` placeholder.
- Every field must have its documented type; nothing is silently coerced. An
  unquoted number where a string is expected (e.g. `subdir: 2024`) is rejected
  rather than ignored — quote it (`subdir: "2024"`). `filters` must be a list,
  even for a single rule (`filters: ["- *.tmp"]`, not `filters: "- *.tmp"`).

Each failure nbkp reports itself carries a stable error code
(`unknown-reference`, `circular-proxy-jump`, `nested-endpoint`, …; see
`ConfigValidationErrorKind` in `nbkp/config/protocol/errors.py`). With
`--output json`, a command that cannot load its config prints this on stdout
instead of the human-readable panel, and exits with code 2:

```text
{"error": {"reason": ..., "message": ..., "errors": [{"loc": ..., "type": ..., "message": ...}]}}
```

A `--location` or `--exclude-location` value that no SSH endpoint declares, a
`--sync` that names no sync, and a `disks --name` that names no volume are
rejected the same way, once the config has loaded: exit code 2, and with
`--output json` the error object
`{"error": {"reason": "unknown-location", "message": ..., "names": [...]}}` (or
`unknown-sync`, `unknown-volume`) on stdout instead of the text on stderr.
