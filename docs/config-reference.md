# Configuration Reference

Every field of the nbkp YAML config file, with its type, default, and validation rules. For users writing a config file who need the exact shape of a section.

For what the entities *are* and how they relate (volumes, endpoints, syncs, snapshots), read [Domain](./domain.md) first. For runtime behavior, see [Internals](./internals.md). For worked examples, see [Usage](./usage.md#config) and [config-examples/](./config-examples/).

The field tables below are generated from the config models by `mise run configdocs`; edit the prose around them, not the tables.

## Config File Location

nbkp searches for the config in this order and uses the first match:

1. Explicit `--config` path
2. `$XDG_CONFIG_HOME/nbkp/config.yaml` (typically `~/.config/nbkp/config.yaml`)
3. Platform user config dir (Linux: same as above; macOS: `~/Library/Application Support/nbkp/config.yaml`)
4. Platform site config dir (Linux: `/etc/xdg/nbkp/config.yaml`; macOS: `/Library/Application Support/nbkp/config.yaml`)

Platform directories are resolved using [platformdirs](https://github.com/tox-dev/platformdirs).

## Volumes

**Path normalization** — Volume paths and sync endpoint subdirectories are normalized at load time: trailing slashes are stripped, so `path: /mnt/data/` and `path: /mnt/data` are equivalent. For local volumes, `~` is expanded to the current user's home directory (`path: ~/data` becomes `/home/user/data`). Remote volume paths are not `~`-expanded: there the tilde refers to the remote user's home and is resolved by SSH/rsync on the remote side.

**`path` and `mount`** — `path` is required unless the volume declares a `mount` section. For a mount-managed volume, declare `path` (backed by an `/etc/fstab` entry) to mount at a fixed location, or omit it to let udisks mount at `/run/media/<user>/<label>`, which nbkp discovers at runtime. There is no `strategy` field (udisks is the only backend) and no `mapper-name` (nbkp discovers the name udisks chose for the unlocked device). See [Volume Mount Management](./internals.md#volume-mount-management) and the [udisks2 setup guide](./usage.md#mount-management-with-udisks2).

#### `mount` — Mount Config

| Field | Type | Default | Description |
|---|---|---|---|
| `device-uuid` | string | **required** | Device UUID for drive detection (from ``/dev/disk/by-uuid/``). For encrypted volumes: the LUKS container UUID (from crypttab/blkid); the unlocked device is named ``luks-<uuid>`` by udisks unless the LUKS2 header carries a label or a crypttab entry overrides it (nbkp discovers the actual name either way). | `encryption` | object | `null` | Encryption config. Omit for unencrypted volumes. |

The `mount` section is optional on both local and remote volumes. When present, nbkp manages the mount/umount lifecycle automatically during `run`.

For encrypted volumes, `device-uuid` is the LUKS container UUID (from `crypttab` or `blkid`). For unencrypted volumes, it is the filesystem UUID (from `fstab` or `blkid`).

#### `encryption` — LUKS Encryption Config

| Field | Type | Default | Description |
|---|---|---|---|
| `type` | `"luks"` | **required** | Volume type discriminator |
| `passphrase-id` | string | **required** | Credential lookup key for the passphrase |

The `type: luks` field is a discriminator for future encryption backend extensibility. Currently only LUKS is supported.

The `passphrase-id` is used as a lookup key with the configured `credential-provider`. Multiple volumes can share the same `passphrase-id` — the passphrase is cached in memory during a single run.

---

Top-level config fields for credential retrieval:

| Field | Type | Default | Description |
|---|---|---|---|
| `credential-provider` | `"keyring"` \| `"prompt"` \| `"env"` \| `"command"` | `"keyring"` | How LUKS passphrases are retrieved |
| `credential-command` | list of strings | `null` | Command template for `command` provider. Must contain `{id}` placeholder (e.g. `["pass", "show", "nbkp/{id}"]`) |

Providers:
- **keyring**: `keyring.get_password("nbkp", passphrase_id)` — uses macOS Keychain or Linux SecretService. Requires `pip install nbkp[keyring]`.
- **prompt**: interactive hidden input prompt.
- **env**: reads `NBKP_PASSPHRASE_<ID>` (uppercased, hyphens → underscores).
- **command**: runs command template with `{id}` replaced by passphrase-id.

## SSH Endpoints

**`extends`** — An endpoint inherits every field of the endpoint it extends and overrides only the fields it sets. Setting one field of a mutually exclusive pair (`proxy-jump` / `proxy-jumps`, `location` / `locations`) drops the inherited other half. Circular `extends` chains are rejected at load time.

**`proxy-jump` / `proxy-jumps`** — Reference other endpoints by slug to reach the host through one bastion (`proxy-jump`) or a multi-hop chain (`proxy-jumps`). Both map to SSH's `-J`. Circular chains are rejected at load time.

**`location` / `locations`** — Network-context tags (e.g. `home`, `travel`) consumed by `--location` / `--exclude-location` at runtime. See [Endpoint Filtering](./internals.md#endpoint-filtering).

**`~/.ssh/config` enrichment** — `port`, `user`, and `key` (first `IdentityFile`, `~`-expanded) are filled from `~/.ssh/config` when not set. Precedence, highest first: explicit value > inherited via `extends` > `~/.ssh/config` > default. `proxy-jump` and `connection-options` are never enriched.

**Connection options** — Typed SSH settings mapped onto the SSH CLI (used by rsync) and onto Paramiko/Fabric (used by checks and snapshot operations). `channel-timeout` and `disabled-algorithms` only apply to the Paramiko/Fabric path. Setting `strict-host-key-checking: false` together with `known-hosts-file: /dev/null` fully disables host key verification and persistence, which suits ephemeral hosts whose keys change on reprovisioning. The resulting SSH flags are listed in [SSH transport](./internals.md#ssh-transport).

## Sync Endpoints

<!-- BEGIN CONFIGREF:SYNC_ENDPOINTS (auto-generated by: mise run configdocs — do not edit manually) -->

| Field | Type | Default | Description |
|---|---|---|---|
| `volume` | string | **required** | Volume slug |
| `subdir` | string | `null` | Subdirectory within the volume. Leading and trailing slashes are stripped. |
| `btrfs-snapshots` | object | see below | Btrfs snapshot config |
| `hard-link-snapshots` | object | see below | Hard-link snapshot config |

Only one of `btrfs-snapshots` and `hard-link-snapshots` can be enabled per endpoint. Each (volume, subdir) pair must be unique across all sync endpoints.

When used as a **source**, enabling snapshots tells rsync to read from the `latest/` directory instead of the volume root. When used as a **destination**, enabling snapshots activates snapshot creation after each successful sync.

**Rsync options** — `compress` and `checksum` are opt-in flags. `default-options-override` replaces the default flags entirely; `extra-options` appends flags after them. Why `--hard-links` is not a default: [Rsync Defaults](./internals.md#rsync-defaults).

#### Filters

Filters can be specified as structured rules or raw rsync filter strings, mixed freely:

```yaml
filters:
  # Structured include/exclude rules
  - include: "*.jpg"          # becomes "+ *.jpg"
  - exclude: "*.tmp"          # becomes "- *.tmp"

  # Merge: read rules from an external file (applied globally)
  - merge: /etc/nbkp/extra-rules.txt
  - merge: ~/my-rules.txt    # tilde is expanded

  # Dir-merge: per-directory filter files (rsync discovers them as it walks the tree)
  - dir-merge: .rsync-filter

  # Dir-merge with exclude-self: equivalent to rsync's -FF
  # (use per-directory filters, but don't transfer the filter files themselves)
  - dir-merge:
      path: .rsync-filter
      exclude-self: true

  # Raw rsync filter strings (for advanced modifiers like ,e or ,n)
  - "H .git"                  # hide .git from transfer
  - "- __pycache__/"          # exclude __pycache__
  - "dir-merge,e /.rsync-filter"  # dir-merge with word-splitting
```

**`merge`** reads a file of filter rules once and applies them at the point where they appear in the list. Tilde (`~`) is expanded in merge paths. This is similar to `filter-file`, but `filter-file` is always appended after all inline filters, while `merge` respects its position in the list.

**`dir-merge`** tells rsync to look for the named file in each directory as it walks the source tree. Rules from each file apply only to that directory and its subdirectories. The `exclude-self` option appends a `- <filename>` rule to prevent the filter files from being transferred (equivalent to rsync's `-FF` flag). Dir-merge paths are not tilde-expanded (they are relative filenames resolved by rsync per-directory).

Filters are applied in order as `--filter=RULE` arguments. When `filter-file` is also set, inline filters are applied first.

## Validation Rules

Checked when the config is loaded, before anything runs:

- Slugs are lowercase alphanumeric with hyphens, at most 50 characters.
- Every slug reference (`ssh-endpoint`, `ssh-endpoints`, `proxy-jump(s)`, `extends`, `volume`, `source`, `destination`) must name an existing entry.
- No circular `extends` or `proxy-jump` chains.
- `proxy-jump` / `proxy-jumps` and `location` / `locations` are mutually exclusive.
- Each sync endpoint targets a unique `(volume, subdir)` pair, and no endpoint may be nested inside another on the same volume (e.g. `subdir: photos` and `subdir: photos/2024`): sync dependencies cannot be detected between overlapping paths.
- At most one of `btrfs-snapshots` and `hard-link-snapshots` is enabled per sync endpoint.
- Each sync endpoint is the destination of at most one sync.
- A remote-to-remote sync must stay on one server: both volumes must use the same primary `ssh-endpoint`.
- A volume without a `mount` section must declare `path`.
- `credential-command` is required when `credential-provider` is `command`, and must contain the `{id}` placeholder.
